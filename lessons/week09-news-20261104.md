## 2 November: Runway packages development tools for coding agents

Runway [announced plugins for Claude Code, Codex and Cursor](https://runway.com/news/developers%2Frunway-dev-plugins-for-coding-agents)
on **2 November 2026**. The package combines its development MCP connection
with skills for building media API integrations. It exposes account/project
information, model availability, prices and limits, plus task error details.
This is a tooling release, not a new generative model or an independently
verified claim that an agent completes every integration correctly.

The [setup guide](https://dev.runwayml.com/learn/build-with-your-coding-agent)
was first published 17 September and updated 2 November. Live generation
requires a Runway Dev account, API credentials and billable credits. The
plugin's account sign-in and the application's generation credentials have
different roles. Do not install it, connect accounts, upload work or make
paid calls for this classroom comparison.

**Week 9 angle:** draw browser -> application -> media provider. Which process
owns the job, which message is a request, and what evidence should the interface
show before claiming success?

Older technical context in the [SDK documentation](https://docs.dev.runwayml.com/api-details/sdks/)
shows a creation request returning a task ID, followed by status/output reads.
Receiving that ID does not establish that the final asset exists. Stopping
the SDK polling wait does not itself cancel the remote task.

## 2 November announcement / 3 November paper: LifeVal

OpenAI [announced LifeVal](https://openai.com/index/lifeval/) on **2 November**;
the linked [research paper](https://cdn.openai.com/pdf/lifeval.pdf) is dated
**3 November 2026**. The paper describes 169 personalized agent tasks and
GPT-5.6-based grading that inspects created artifacts and changes in backend
state, alongside the response. See sections 3.3, 3.5 and 4.

This is OpenAI's own evaluation research, not independent evidence or a newly
released classroom app. Its task environments and offline web recreate
workflows; benchmark results do not prove completion on arbitrary live sites.
The public paper is sufficient for this discussion. No benchmark installation,
personal data or agent account is needed.

**Week 9 angle:** if an agent says "I changed the artwork", what observation
would distinguish a written claim, a transmitted request, an application
acknowledgement and the actual shared scene state?

## Optional paper comparison, not a live demo

Use fictional data and label the trace **paper simulation**:

1. A request returns a made-up provider task ID. The job is still pending.
2. Hide the next status response. Ask whether the client can conclude success,
   failure or cancellation.
3. Restore observation with a status read. Compare this with the existing
   tutorial's reconnect/snapshot reasoning and its uncertain-action case.

A provider task ID identifies remote work. The existing scene's client action
ID correlates a response and does not deduplicate retries. A current state
snapshot is not a receipt for one particular command. Missing observation
does not make blind resubmission safe.

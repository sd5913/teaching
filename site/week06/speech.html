Speech synthesis and transcription

Start with a finite Python console transcript. Then move the microphone into a local browser app over WebRTC. Correct the proposed words before asking an optional local model to respond. Speech synthesis is a separate extension, not an automatic voice loop.

No microphone starts from this static page. The local Streamlit app asks for browser permission only after you click START. First use downloads libraries and model weights. Local inference needs no classroom API key. Model inference and actual microphone hardware still need a classroom-device rehearsal.

Before class

Open the PFAD speech scripts and setup instructions. Use the separate Python 3.12 environment in week06/speech; the repository’s root environment belongs to the Week 4 Worker.

  • The primary examples use kokoro==0.9.4 and faster-whisper==1.2.1 on CPU. Their installed dependencies and model files need a preflight before a live lesson.
  • Kokoro needs PyTorch, language resources and espeak-ng. Microphone capture uses sounddevice/PortAudio and the operating system’s microphone permission. A server or remote notebook does not automatically receive your browser’s microphone.
  • Download and test the models ahead of time. --check checks prerequisites without loading model weights or recording. It cannot prove that a model will run successfully.
  • Keep a short PCM WAV you have permission to use. The file-input exercise needs no microphone. Neither script plays audio automatically.
cd week06/speech
uv run --no-project synthesise.py --check
uv run --no-project transcribe.py --check

The following commands assume the PFAD setup is complete and the terminal stays in this folder. Use a new output name for each comparison; existing results are preserved.

1. A file to a proposed transcript

uv run --no-project transcribe.py \
  --audio out/cue.wav --out out/cue.txt

faster-whisper runs the English base.en model using CPU int8 computation. Its file decoder resamples audio to mono 16,000 samples/s. Resampling changes the sample sequence correctly; merely changing the rate label would change playback speed and pitch.

Compare the printed and saved transcript with your original sentence and the actual audio. A correct transcript does not prove natural pronunciation. An error may come from the voice, the recognizer, or the way the words were recorded.

Speech recognition can hallucinate words, especially around silence or noise. Treat the text as a prediction until you check it. Do not use this classroom prototype as a verbatim record of someone else’s words.

2. A bounded Python console transcript

Record yourself, or get the consent of anyone whose voice might be captured. Start only when the room is ready. This command records continuously for three 5-second chunks, then closes the microphone:

uv run --no-project transcribe.py --microphone \
  --chunks 3 --seconds 5 --out out/mic.txt

The microphone supplies mono 16 kHz samples while the local model processes queued chunks. Text arrives after each chunk and can lag on a slow machine. Ctrl+C stops the demo. The complete script bounds recording, queue memory and waits for the capture device.

This is chunked near-live transcription. It does not promise native streaming, immediate partial words or seamless sentence boundaries. A word split across two chunks may be lost or changed. Longer chunks give more context but delay feedback.

If microphone permission or the input device fails, use the file example above. Do not publish recordings or transcripts of classmates. The exercise adds no assessed submission.

3. Put the microphone in a browser with WebRTC

The console program reads a microphone attached to Python's own machine. For a browser microphone, the PFAD local Streamlit WebRTC app receives a WebRTC audio track, converts frames to mono 16 kHz, and calls the same kind of finite base.en transcription in 3-second chunks. Its separate requirements are optional and do not change the Week 4 Worker or deckgen environment. The teaching preview also offers a source download.

cd week06/speech
uv venv --python 3.12 .venv-webrtc
uv pip install --python .venv-webrtc/bin/python -r speech_webrtc_requirements.txt
.venv-webrtc/bin/python -m streamlit run speech_webrtc.py --server.address 127.0.0.1

First warm the same base.en cache with the PFAD file transcription on your own computer. In the local app, load the cached model, click START and permit the microphone, speak briefly, then click STOP. Processing is limited to three 3-second chunks. STOP is still necessary to end the browser media track if processing ends first. The app keeps transcripts in its local session, not WAV files. A browser on a remote computer would need HTTPS and likely STUN/TURN; this localhost example is not a published multi-user app.

The static course preview links the PFAD Python source; it cannot run the local model or accept a microphone. If WebRTC, the model or permissions fail, use the already-tested file-input path. Neither browser capture nor actual inference has been verified on the teaching device.

4. Check before a response

After STOP, inspect and correct the proposed transcript. The app contacts only local Ollama at 127.0.0.1:11434, and only if you press its Ask button. It requests a one-sentence text reply from a locally installed qwen3:4b model. Ollama is optional and was not run in this lesson validation; if it is unavailable, ask the class to write a response to the corrected sentence instead. Do not treat an incorrect transcript as an instruction, and do not imply that the app speaks its answer automatically.

Change one sentence in the console exercise and then in the browser. What is the same about the model's input? What changes about capture, consent, timing and stopping? The visual/no-listening route remains the WAV metadata and written transcript.

Optional extension: text to a spoken cue

Predict how a spoken file-save notification will feel. Keep the wording short and use the preset synthetic voice.

uv run --no-project synthesise.py \
  --text "Your file is ready." \
  --speed 1.0 --out out/cue.wav

Kokoro uses KPipeline(lang_code="a", device="cpu") and the preset af_heart. The script keeps all generated chunks, then saves a mono PCM WAV at 24,000 samples/s and a settings record. Open the saved file yourself at low volume.

Change only --speed 1.0 to --speed 0.85 and save out/cue-slower.wav. Does it feel clearer, calmer or more interruptive? The numeric setting does not guarantee an exact duration. Check pronunciation as well as tone.

A small design experiment

  1. Keep one sentence, its WAV, settings and transcript as a reference.
  2. Change one synthesis parameter. Predict what a listener will notice.
  3. Compare the second audio and transcript. Which result is useful evidence for your prediction?
  4. Sketch an interface that lets a person correct a transcript or stop a spoken cue.

The visual route is to inspect the sentence, sample rate, duration and transcript. Listening or microphone use is optional.

Other speech synthesis options

Kokoro is the main exercise so everyone can discuss the same inputs and settings. Optional alternatives have different installation, hardware and licensing requirements.

  • Piper: a local CPU voice for interface prompts. The current engine is GPL-3.0-or-later; inspect the chosen voice’s own model card and license.
  • Chatterbox: expressive dialogue and delivery cues. Current upstream Nano/V3 options may not exist in the published 0.1.7 wheel. Hardware and checkpoint choice need their own tested setup.
  • Qwen3-TTS: multilingual voice design and delivery instructions, with different controls for different checkpoints. Its larger models suit a prepared demonstration rather than an assumed fast CPU exercise.

Compare the same text for pronunciation, controllability, delay and resource use. Check the actual model license as well as the Python package. These are options to investigate, not a quality ranking or a claim that they were run here. Use preset or designed voices; reference-speaker experiments require that person’s permission for the intended use and sharing.

KittenTTS needs a version label

The older KittenTTS 0.8.1 API can use mini-0.8, an approximately 80 MB model. That is a legacy English example. It is distinct from KittenTTS 2, a much larger multilingual model with a different API and weights license. Do not apply an old “25 MB” claim to the current model. Neither is installed or benchmarked for this lesson.
